# ADR-0014: 显式模型选择与能力预检

- 状态：已接受
- 日期：2026-09-07

## 背景

ADR-0013 已把模型按用途绑定，但用户仍只能接受默认部署。Chat 用户需要在快速／质量预设或具体 Profile
之间做一次明确选择；同时，能被配置不代表模型已经证明支持工具、原生流、结构化输出或 reasoning。
若选择和能力检查藏进 Adapter，业务无法在请求前解释失败，Trace 也无法证明最终执行了哪个模型。

## 决策

1. 用户选择是运行输入：具体 Profile 与 fast／quality 预设互斥，预设只是确定性 Profile 别名。
2. 选择由应用控制面解析并在真实运行边界冻结；Web 按 Chat turn 冻结，CLI ReAct 按会话冻结。
3. 真实消费者声明最低能力需求；Profile 对每项能力记录 supported、unsupported 或 unknown。
4. 显式选择同时对 unsupported 与 unknown 大声失败，不移除工具、降级模拟流或改写请求来迁就模型。
5. 明确选择的 Profile 不被默认绑定、路由或故障恢复静默替换；旧调用不传选择仍走原默认路径。
6. `model-identity.v1` 记录实际选择来源和配置／策略指纹，继续贯通 AgentEvent、Trace、Replay 与 Eval。

本决策只开放 Chat 与 CLI ReAct 两个有明确冻结边界的消费者。出题、判卷、Reader 与 Eval 继续使用各自
用途绑定，不被某次 Chat 选择连带覆盖。

## 备选方案

- 根据模型名自动推断能力：接入省事，但兼容 endpoint、模型版本和账户开关会让推断迅速失真。
- unknown 乐观放行：短期兼容面大，但失败发生在可能已计费的网络请求后，也无法区分配置缺失。
- 预设由运行时动态排名：尚无质量、费用与延迟 Eval，无法给出可审计的选择依据。
- 把选择保存在学习事实：模型部署偏好不是学习领域事实，且首版没有跨设备持久化消费者。

## 后果

用户意图、能力不足和最终执行身份现在都可在请求前解释和在历史中复核。代价是显式选择要求配置维护者
声明能力；未声明时按 unknown 拒绝。当前预设不承诺性能。传输 retry 后由
[ADR-0015](0015-application-owned-provider-retry.md) 定义；显式选择仍不会授权跨模型 fallback，动态路由
与新协议 Adapter 也必须按各自进入门单独验收。
