## 一、出发点：为什么做"自进化"

作者是本工具的用户 #1，每天用 `grandquiz react` 考自己。用久之后有两处体验天花板：

1. **考核形态僵死**——一次 `start_quiz(count=N)` 只能出一种题型，做不到"先几道选择热身、再几道
   简答深入"的分段节奏。
2. **难度不会长进**——一个概念无论掌握得多熟，出的题永远一个难度；越学越熟，题却原地踏步，
   考核逐渐失去"拷问"的价值（而"拷问"正是产品核心循环的立身之本）。

且系统即便调整了行为，对用户也是黑箱。故本阶段目标：**让考核能按掌握程度自我调难，并把每次
自我调整透明地展示给用户**——这就是"自进化"在本项目的具体含义（数据驱动 + 确定性规则 + eval
可验证，**不是** agent 自改代码）。

## 二、这一阶段做了什么

### 1. 规划（grill-with-docs → PRD → 6 issues）
一轮对抗式追问，把三个悬而未决的设计问题逼出答案后落成 PRD，切成 6 个竖切增量：
S1 难度台账 → S2 跨档规则 → S3 采集接线 + 透明展示 → S4 批内分段调度 → S5 选择题难度杠杆 →
S6 开放/追问难度杠杆。复习排期（spaced repetition）明确切出范围、留待以后单独讨论。

**三个拍板的关键决策**：
- **难度是离散 5 档、不是连续分数**——守 `CONTEXT.md` 全仓库"三态状态机 / 三值判决、无掌握度
  分数"的一贯哲学，难度不做第一个例外，也天然适合 eval 断言。
- **难度存一张独立新表、不塞进 Learning Memory**（本轮讨论最大的架构发现）——Learning Memory
  薄弱台账"销账即删记录"，而难度需要在概念销账后依然保留（甚至一路顺畅、从没薄弱过的概念也要
  标难度并升档），生命周期更长、形状不同，必须另立一张"只要考过就一直在"的表。
- **批内分段调度复用 ADR-0006 的 `resolve_question_type`、不新造裁决**——只是把"一次调用一个
  全局题型意图"换成"每个位置各自一个意图"，"用户显式意图胜过自适应路由"这条既有规则原样成立。

### 2. 实现（SE-S1 + SE-S2 难度引擎地基，本次已合入）
两个可独立单测的**确定性单元**，构成难度自适应的地基（此刻还没有生产消费者——那是 S3 的接线）：

- **SE-S1 难度台账**：`DifficultyLedger` 协议 + `DictDifficultyLedger`（内存）+
  `SqliteDifficultyLedger`（持久，跨会话留存），锚定 `item_id` 存离散档位。
- **SE-S2 跨档规则**：`next_tier` 纯函数，据三路信号裁决一个概念升 / 降 / 维持一档。

### 3. 对抗性自审（本阶段刻意的一道工序）
地基由 AFK 后台 agent 以 TDD 实现、六门自证全绿后，主线程**逐行重读 + 实际执行代码**做对抗审查，
逮到三处并修正（详见下方"实现方法"末尾）——**发现的都在"测试诚实度 + 描述准确度"层，无功能 bug**，
印证了"AFK 实现 + 独立对抗审查"这套双层工序的价值。

## 三、实现方法（简要）

### 难度台账（SE-S1）
照仓库已成熟的 **Protocol + Dict + Sqlite 三段式**先例（`asked_questions.py`）：一个 `Protocol`
定契约（`tier_of` 读、未记录过返回默认档 3；`set_tier` 幂等写覆盖），一个内存实现供测试，一个
SQLite 实现供生产。migration `0006_difficulty.sql` 建表——**无时间戳列**（determinism 纪律，
排序靠 `seq` 自增主键），复用 kernel 参数化 `migrate`（按 `PRAGMA user_version` 增量应用）。
难度是"当前状态"语义，故 `set_tier` 用 `INSERT OR REPLACE` 后写覆盖（与 asked_questions 的只增
语义相反）。

### 跨档规则（SE-S2）
纯函数 `next_tier(current, signals)`，照 `memory.py` 的 `apply_verdict` 风格——无 I/O、不碰
随机/时钟、同输入恒同输出。三路信号各投一票 ∈ {+1 更熟 / 0 中性 / −1 更虚}：

| 信号 | +1（更熟） | −1（更虚） | 来源 |
|---|---|---|---|
| 销账轮数 | ≤2 轮（很快掌握） | ≥4 轮（来回拖） | 被删 `ConceptRecord.verdict_history` 长度 |
| 判决分布 | 无勉强 | 掉过"勉强" | `verdict_history`（三值判决，非分数） |
| 答题耗时 | ≤30s | ≥120s（None 则弃权） | 既有 trace `QUESTION_ASKED`→`ANSWER_JUDGED` 时间戳差，**零新埋点** |

净分 ≥ +2 升一档、≤ −2 降一档，其间维持；**每次至多跨一档**（单步、稳），边界钳制 [1,5]。
阈值全部集中为模块常量，S3 接线后重调只动一处。

**对抗审查暴露的真实语义**（已在 docstring/注释诚实化）：判决轴恒投 ±1（每个销账概念必有判决
历史，这一路永不中性），故规则的真实含义是 **"判决基线 ±1 + 一路速度/轮数佐证推过门限"**，
而非字面的"两路彼此独立的信号同向"。由此有一个**刻意的升降不对称**：清爽销账 + 单个负向佐证
（如一次偶然慢）只维持、不降档——只有真的掉过"勉强"才会降。这个不对称对得上 PRD 的用户故事
（快速反复答对→更难；磕绊多轮→别急着加、甚至降），是 feature 不是 bug。

### 对抗审查修正的三处
1. **措辞**：把 `next_tier` 里"至少两路信号同向才跨档"这个不准确的描述全线改成诚实版本（见上）。
2. **删假测试**：`test_only_fast_holds` 是 `test_fast_but_struggle_holds` 的逐字节重名副本、且其
   声称的性质（"单路快只维持"）实际为假（清爽+快→升档）——删掉，换成三条诚实钉死真实不对称
   的测试。
3. **去冗余索引**：`0006` 里多余的 `CREATE INDEX`（`item_id UNIQUE` 已隐式建唯一索引，是从
   `0005` 抄来但那里 item_id 非唯一才需显式索引）。
