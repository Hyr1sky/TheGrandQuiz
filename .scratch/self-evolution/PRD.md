# PRD：自进化第一阶段（批内分段调度 + 难度自适应 + 透明展示）

Status: in-progress（协作学习式开发——搭骨架 + 讲原理 + 守门，竖切逐增量推进；2026-07-14 起）
Triage: ready-for-agent

> 本 PRD 是 2026-07-14 一轮 `grill-with-docs` 讨论的产出，三个待定设计问题已全部拍板。
> **复习排期（spaced repetition）明确不在本期范围**——见 Out of Scope。

## Problem Statement

作者（用户 #1）每天用 `grandquiz react` 考自己，用久之后有两处体验天花板：

1. **考核形态僵死**：一次 `start_quiz(count=N)` 只能出**一种**题型。想要"先来 3 道选择题热身、
   再来 2 道简答深入"这种一轮里分段推进的节奏，现在做不到——只能拆成两次工具调用，交互割裂。
2. **难度不会长进**：一个概念无论掌握得多熟，出的题永远一个难度。选择题的干扰项始终一样好认，
   开放题始终一个深度。用户越学越熟，题却原地踏步，考核逐渐失去"拷问"的价值——而这正是产品
   核心循环（`CONTEXT.md`「考核循环」）的立身之本。

且系统"自进化"了什么对用户是黑箱：即便难度真的调了，用户也无从知道系统据什么、在何时改了它。

## Solution

给考核循环加三样东西，全部复用既有确定性地基、不引入新范式：

1. **批内分段调度**：`start_quiz` 支持"按题目位置分段指定题型"（第 1~k 题选择、之后简答……），
   仍是逐题交互（**不是**批量出卷，见 `CONTEXT.md`「考核循环」已澄清的 `_Avoid_`）。裁决沿用
   ADR-0006 的 `resolve_question_type(intent, state)`——把"一次调用一个全局 intent"换成"每个位置
   各自一个 intent"，每题仍走同一函数解析，"用户显式意图胜过自适应路由"这条规则原样成立。

2. **难度自适应**：给每个 KnowledgeItem 维护一个**离散 5 档难度**（不是连续分数——见下方决策），
   由一条**确定性规则**据三路信号（销账花了几轮 / 答题耗时近似 / 判决分布）判断该不该跨档；
   难度落到出题时**不对称**——选择题走结构性 + judge 闸门的硬杠杆，开放/追问走提示词软杠杆。

3. **透明展示**：难度跨档时发一个新领域事件 `DIFFICULTY_TIER_CHANGED`，走既有事件脊柱、由
   `QuizEventPrinter` 渲染——照 `CONCEPT_STATE_CHANGED` 的先例，让"系统改了什么"可见。

全程确定性可 replay：难度台账是纯 SQLite、跨档规则是纯函数、信号来自既有 trace 事件、
LLM 只在出题/judge 两个既有有界槽里被调用（Record/Replay + cassette）——replay 对得齐。

## User Stories

1. 作为用户，我想在一次考核里指定"前几道选择、后几道简答"，这样一轮就能既热身又深入，不用拆成
   多次触发。
2. 作为用户，我说"考我 5 题，先 3 道选择再 2 道简答"时，我想系统按这个分段顺序逐题问我。
3. 作为用户，当我没指定分段（只说"考我 5 题"）时，我想行为跟现在**一字不差**——每题按概念状态
   自适应路由，不受本特性影响。
4. 作为用户，当我对某个位置指定的题型是系统词表里没有的说法时，我想它 fail-soft 回落到自适应
   路由（跟 ADR-0006 现有行为一致），而不是报错炸掉整轮考核。
5. 作为用户，当我把一个概念反复答对、很快销账时，我想系统认为我掌握得好、下次给我更难的题。
6. 作为用户，当我一个概念答得磕磕绊绊（掉进过"勉强"、来回好几轮才销账）时，我想系统别急着加难度，
   甚至该降下来，让我先站稳。
7. 作为用户，当我某个概念难度升档后，我想选择题的干扰项变得更难辨（更多、更像真的），而不只是
   系统内部记了个数字。
8. 作为用户，当难度升档后，我想开放题/追问也往更深处问，而不是停留在表层复述。
9. 作为用户，当系统调整了某个概念的难度时，我想它**当场明确告诉我**（"『闭包』难度：3 档 → 4 档，
   因为你连续 2 次快速答对"），而不是悄悄变。
10. 作为用户，我想难度是"简单→困难"这样一目了然的档位，而不是一个我读不懂的 0.73 分数。
11. 作为用户，我想难度跨会话留存——今天把某概念练到 4 档，明天重开 CLI 它还是 4 档，不会重置。
12. 作为用户，即使一个概念我从没答错过（从没进过薄弱台账），我也想系统能给它标难度并往上调——
    "一路顺畅"本身就是"可以更难"的信号。
13. 作为开发者，我想难度状态独立于 Learning Memory 薄弱台账存放，这样"销账即删记录"的既有契约
    不被破坏，难度也不会随销账丢失。
14. 作为开发者，我想跨档判定是一个可单测、可 mutation-kill 的纯函数，这样它作为 eval 命门可回归。
15. 作为开发者，我想难度对出题的影响里，选择题这条尽量走确定性验收（选项数 + judge 闸门），
    这样"难度真的生效了"是可断言的，而不是全赌提示词。
16. 作为开发者，我想开放/追问这条的"软"如实标注出来，不假装它跟选择题一样确定，避免自欺。
17. 作为开发者，我想难度 judge 复用既有 `role="basic"` 判官模型（跟出题的 `enrich` 模型天然不同），
    不为它新开第三个角色配置。
18. 作为开发者，我想透明展示复用 `CONCEPT_STATE_CHANGED` 的事件脊柱先例，不发明新的展示通道。
19. 作为用户，我想答题耗时的采集不给我增加任何额外操作（不用手动计时），系统自己从考核过程里估。
20. 作为开发者，我想"答题耗时"v1 直接吃现有 trace 的事件时间戳差值，不新埋点，先把闭环跑通再谈
    降噪。

## Implementation Decisions

### 决策 1：难度是离散 5 档，不是连续分数（硬约束）

- 难度是 5 档离散枚举（拟：`1..5` 或 `很简单/简单/标准/困难/很困难`，具体命名留 issue 定）。
  **不做连续分数**——这条来自 `CONTEXT.md`「薄弱概念」`_Avoid_: 掌握度分数（用状态机不用连续分）`
  与「判决」`_Avoid_: 评分、分数`，是贯穿全仓库的设计哲学（三态状态机、三值判决）。难度不能成为
  第一个连续分例外。离散档位也天然适合 eval 断言（"该不该跨档"是可判定命题）。

### 决策 2：难度存在一张新表，独立于 Learning Memory（本次讨论最大的架构发现）

- **不能塞进 `memory.py` 的 Learning Memory 表**：那张表契约是"销账即整条删除 `ConceptRecord`"
  （只追踪薄弱/观察中概念），而难度需要在概念**销账之后依然保留**——甚至一个从没薄弱过、一路
  顺畅掌握的概念（从不进 Learning Memory）也需要标难度并升档（User Story 12）。难度的生命周期是
  "**只要考过就一直在**"，比 Learning Memory 长且形状不同。
- 因此新建一张**难度台账**：锚定 `item_id`，与薄弱台账并列、互不干扰，不随销账删除。
- 协议形状照 `asked_questions.py` 的 **Protocol + Dict + Sqlite 三段式**先例：一个 `Protocol` 定契约、
  一个 Dict 内存实现（测试/快速用）、一个 Sqlite 持久实现（跨会话留存，User Story 11）。新 migration
  文件（承接 `0005_asked_questions.sql` 之后，编号 `0006`）。**无时间戳列**（沿用项目 determinism
  纪律，排序用 `seq` 自增主键）。

### 决策 3：跨档由一条确定性纯函数据三路信号裁决

- 纯函数（拟 `next_tier(current_tier, signals) -> tier`），无 I/O、不发事件、不碰随机/时钟——照
  `apply_verdict` 的样子做成缝的命门单元。三路信号：
  1. **销账轮数**：`ConceptRecord.verdict_history` 的长度，**只在销账那一刻**（`apply_verdict`
     返回 `None` 的转移）可得——销账后记录连同 history 被整条删除，事后无法回读，故**必须在
     `CONCEPT_STATE_CHANGED` 发"销账"转移的那一刻捕获**。
  2. **答题耗时（近似）**：v1 吃既有 trace 里 `QUESTION_ASKED` → `ANSWER_JUDGED` 的时间戳差值，
     **零新埋点**。噪声（用户中途离开）v1 不特殊处理——先跑通闭环，降噪留后续。
  3. **判决分布**：从 `verdict_history` 读——全程"对"没掉过"勉强" vs 反复横跳，是"答得稳不稳"的
     信号，**不新造"答案质量分数"**（复用既有三值判决，遵守「判决」`_Avoid_: 评分、分数`）。
- 合成规则的具体阈值/加权留 issue 设计，但输出恒为离散"新档位"（可能等于旧档 = 不变）。

### 决策 4：难度落到出题——不对称的双腿

- **选择题（硬杠杆，尽量确定性）**：
  - ①档位越高、**干扰项数量越多**——`MultipleChoiceQuestion.options` 本就是不定长列表，
    **不改 schema**；档位 → 目标选项数是确定性映射。
  - ②**复用 Tier-2 干扰项 judge（`judge.py`）当验收闸门**：档位越高，出题后要求 judge 判定
    "干扰项够难辨"（`DistractorLabel` 达标）才通过；不通过 → 重新生成，形成
    **生成 → judge → 不够格重生成**的小闭环。跟出题槽现有校验门（`ungrounded_citations` 不过就
    `ModelRetry`）是同一模子。
- **开放题 / 追问（软杠杆，如实承认）**：
  - 没有像"选项数"那样干净的结构性杠杆。主要靠**提示词（few-shot）按档位给不同难度提示**。
  - 可选的部分确定性辅助：档位越高，要求引用 `KnowledgeItem.evidence` 里**更不常被引用的证据条**
    （深挖冷门细节，是可判定的）。但这条**比 MC 软**，PRD 如实标注——不假装开放题也能做到跟 MC
    一样确定性。
- **判官模型不新开角色**：难度 judge 复用 `judge.py` 已建立的 `role="basic"` 调用（跟判卷官同角色/
  模型）。出题槽固定 `role="enrich"`、判官固定 `role="basic"`，两者本就是不同模型（如 qwen vs
  deepseek），已满足"不能自己判自己"。`Role = Literal["basic","enrich"]`（`providers/base.py`）
  **本期不改**。

### 决策 5：批内分段调度——复用 ADR-0006，不新造裁决

- `start_quiz` 的 `question_type` 从"整批一个值"扩成"按位置分段"（具体入参形状——如
  `[(count, intent), ...]` 分段列表——留 issue 定）。展开成"每题一个 intent"后，**每题仍调
  `resolve_question_type(intent, state)`**：命中词表 → 用户意图胜出（ADR-0006），未知/None → 回落
  `route_question_type` 自适应。**无新裁决逻辑**。
- 无分段（现有单值/缺省）路径**逐字节等价于改动前**——message / replay_key / prompt 版本 / golden
  cassette 一字不变（同 ADR-0006 的 `question_type=None` 缺省契约）。
- `start_quiz` 工具 description 教 LLM 如何把用户的"先 X 再 Y"意图抽成分段结构（延续 ADR-0006 里
  "LLM 只抽意图短语、代码映射"的分工）。

### 决策 6：透明展示——新事件 `DIFFICULTY_TIER_CHANGED`

- 跨档规则触发实际跨档时，在 `LearningEvent` 加一个 `DIFFICULTY_TIER_CHANGED` 常量，经
  `EventEmitter.emit` 上脊柱，payload 含 `item_id / concept / from_tier / to_tier / reason`（reason
  为据哪路信号跨档的简短说明）。`QuizEventPrinter` 订阅渲染。照 `CONCEPT_STATE_CHANGED` 先例——
  **无转移时不发**（只在真跨档时发，避免噪声）；kernel 不认识该事件类型（领域无关脊柱）。

### 决策 7：反馈飞轮——本期不做新机制

- tingle.md 原列的"反馈飞轮"经判定为**框架已就绪**：R3 已建的偏好推断模式
  （`preference.py` 的 `detect_language` / `record_inferred_preference`，confidence 递增 / 遇不一致
  归零）就是它的雏形。本 PRD 只**点明**"以后新增可推断维度时复用此模式"，不展开设计新机制、
  不产出 issue。

## Testing Decisions

好测试只断言**外部可观测行为**（返回值、发出的事件序列、跨会话持久结果），不断言实现细节。

- **难度台账**（决策 2）：照 `test_asked_questions.py` 先例——读写、Dict↔Sqlite parity（同序同值）、
  跨会话持久（重开连接仍在）。走 TDD。
- **跨档规则纯函数**（决策 3）：本期**最该重投入单测**的确定性核心。TDD 红-绿-重构，覆盖每路信号
  单独触发升/降/不变、边界档（1 档不再降、5 档不再升）、三路信号组合，各 mutation 可杀。照
  `apply_verdict` 的纯函数单测路数（`test_memory.py` 那类）。
- **批调度展开纯函数**（决策 5）：分段列表 → 每题 intent 的展开逻辑做成纯函数，TDD 单测
  （空/单段/多段/count 对不齐边界）。照 `test_routing.py` 对 `resolve_question_type` 的测法。
- **MC 难度杠杆**（决策 4 选择题）：LLM 槽，**不 unit-TDD**——走 Record/Replay 录放 + eval harness，
  照 `test_judge_distractor_replay.py` 先例。断言外部行为：档位越高、请求的目标选项数越多；judge
  不达标触发重生成。
- **开放/追问难度杠杆**（决策 4 软腿）：同样不 unit-TDD，靠 eval harness 断言"不同档位确实走了不同
  prompt 变体 / 引了不同证据条"。**如实标注这条比 MC 软、断言更粗**。
- **透明展示事件**（决策 6）：照 `CONCEPT_STATE_CHANGED` 的断言方式（检查 emitted 事件列表里
  `DIFFICULTY_TIER_CHANGED` 的存在与 payload）——真跨档才发、不跨档不发。
- **缺省路径回归**（决策 5）：无分段调度时既有 assess/react eval 用例 + golden cassette **逐字节绿**
  （证明加法式演进、零行为漂移）。

## Out of Scope

- **复习排期 / spaced repetition**（"多久之后复习"、主动提醒）：`CONTEXT.md`「考核循环」明确
  `_Avoid_: 复习计划（MVP 无排期概念）`。用户认为这需要高度定制、闭门造车易做出用户不想要的方案，
  明确留待以后单独一轮讨论。本期**完全不碰**。
- **答题耗时降噪**：v1 用裸时间戳差值，不处理"用户中途离开"噪声。降噪策略留后续。
- **新增第 4 题型 / 独立"简答"题型**：延续 ADR-0006，复用既有三题型（选择/开放/追问），不新增。
- **难度 judge 独立模型角色**：不加第三个 `Role`，复用 `basic`。
- **反馈飞轮新机制**：框架已就绪（决策 7），本期不产新代码。
- **难度影响选题优先级**：本期难度只影响"出的题多难"，**不改**选题（`select_target`）——选题仍由
  Learning Memory 薄弱优先驱动。难度与选题解耦，避免一次动两个子系统。

## Further Notes

- **增量顺序（竖切先穿透）**：SE-S1 难度台账（地基）→ SE-S2 跨档规则纯函数（命门）→ SE-S3 信号采集
  + 记账接线 + 透明展示事件（把 S1+S2 接进真实考核编排、点亮事件脊柱——此时难度已会变会显示，
  即使还没影响出题）→ SE-S4 批内分段调度（正交，可并行）→ SE-S5 MC 难度杠杆 → SE-S6 开放/追问
  难度杠杆。S3 完成即是一条会自进化 + 透明展示的**可感知竖切**，S5/S6 再让难度真正落到题面。
- **determinism 纪律**：难度表无时间戳列（`seq` 排序）；跨档规则纯函数无 clock/random；耗时信号
  来自既有 trace 时间戳（replay 下由 `ManualClock` 提供，确定）。
- **分层守卫**：全部落在 `domain/learning/`，不碰 kernel（难度是领域概念）。`DIFFICULTY_TIER_CHANGED`
  是领域事件字符串，经 kernel 泛型 `emit` 上脊柱，kernel 不认识它——延续脊柱设计。
- **prompt 漂移 → 重录 cassette**：S4/S5/S6 若改动 `start_quiz` 工具 description 或出题 prompt，
  相关 golden cassette 的内容 hash 变 → 按项目惯例重录（这是设计信号，不是 bug）。
